## 1. Product overview

Build a mobile-first, interactive wedding invitation website shared through one public URL. Guests can view the invitation, wedding details, photos, countdown and directions; confirm attendance; leave an optional message; and view separate gift QR codes for the bride and groom.

The website is for a personal, non-commercial event and should operate continuously for at least one month. It must remain lightweight, inexpensive within free-tier limits, easy to maintain through Codex on a phone or laptop, and portable to another hosting provider.

## 2. Approved scope

### Guest experience

1. Interactive envelope opening.
2. Hero section with the couple's names, primary image and invitation wording.
3. Responsive wedding photo gallery.
4. Wedding date, time, venue and Google Maps link.
5. Countdown to the event.
6. Lightweight scroll reveal and parallax effects.
7. Optional background music with a visible play/pause control.
8. RSVP form.
9. Two gift QR cards, one for the bride and one for the groom, each with its own image and save action.
10. Clear loading, success and recoverable error states.
11. A short privacy notice explaining that RSVP information is collected only for event organization and is visible to the hosts.

### RSVP fields

- `submissionId`: UUID generated by the client and reused for retries.
- `clientId`: UUID stored locally on the device.
- `guestName`: required guest name.
- `guestSide`: `BRIDE` or `GROOM`.
- `attendance`: `YES` or `NO`.
- `message`: optional greeting/message.

There is no guest-count field. It must not appear in the form, API contract, validation, spreadsheet columns, summary formulas, tests, or documentation.

### Explicitly outside the MVP

- Guest login or account registration.
- Individual invitation links or invite codes.
- Guest-count selection.
- Public guest list or public read API.
- Separate administration dashboard; Google Sheets is the MVP management interface.
- Public guestbook; consider it only in a later phase.
- Bank API integration, payment verification, or automatic gift tracking.
- Multi-template invitation builder.
- Spring Boot, PostgreSQL, Redis, Docker, queues, or other unnecessary infrastructure.

## 3. Visual and interaction direction

Use `https://ngaychungdoi.com/` and its invitation gallery only as product/interaction references. Do not copy proprietary code, templates, imagery, brand assets, or distinctive copyrighted compositions.

Prioritize the emotional sequence:

1. Open the envelope.
2. Discover the invitation while scrolling.
3. View photos and event information.
4. Confirm attendance.
5. Optionally view/save a gift QR.

Design requirements:

- Mobile-first and responsive.
- Smooth on iOS Safari and Android Chrome.
- Accessible semantic HTML, keyboard controls and readable contrast.
- Support `prefers-reduced-motion` by removing or reducing nonessential motion.
- Do not autoplay audio before user interaction.
- Lazy-load noncritical images and optimize media formats/sizes.
- Prefer CSS animations, Vue transitions and Intersection Observer.
- Use GSAP only if an approved animation cannot be implemented cleanly with lighter tools.
- Keep parallax and decoration subtle; readability and performance are more important than spectacle.

The final colors, fonts, images and exact theme remain configurable and will be selected before full UI implementation.

## 6. RSVP API contract

Endpoint:

```http
POST /api/rsvp
Content-Type: application/json
```

Example request:

```json
{
  "submissionId": "e5b70530-4a93-47c8-98d1-63f8951bc438",
  "clientId": "8e7f5e0e-ab22-4e99-a999-58a0add81d71",
  "guestName": "Nguyen Van A",
  "guestSide": "BRIDE",
  "attendance": "YES",
  "message": "Wishing you both a lifetime of happiness!"
}
```

Validation rules:

- Both identifiers must be valid UUIDs.
- `guestName` is required and should be limited to a reasonable length, for example 2ƒ?"100 characters.
- `guestSide` accepts only `BRIDE` or `GROOM`.
- `attendance` accepts only `YES` or `NO`.
- `message` is optional and should be limited to 500 characters.
- Limit request body size.
- Generate `submitted_at` on the server.
- Sanitize values that begin with spreadsheet formula characters.
- Do not expose Google API or credential details in responses.

Suggested response behavior:

| Status | Meaning |
|---|---|
| 200 | Recorded, or the same `submissionId` was already recorded |
| 400 | Invalid payload |
| 405 | Unsupported method |
| 429 | Rate limit or anti-abuse control rejected the request |
| 503 | Google Sheets temporarily unavailable |

The client keeps the same `submissionId` while retrying a single submission. Duplicate detection is best-effort: Google Sheets has no transactional unique constraint, so the system does not promise exactly-once writes.

## 7. Google Sheets design

Use one private spreadsheet with three tabs:

- `BRIDE_RSVP` ƒ?" guests who selected `BRIDE`.
- `GROOM_RSVP` ƒ?" guests who selected `GROOM`.
- `SUMMARY` ƒ?" host-facing formulas and counts.

`BRIDE_RSVP` and `GROOM_RSVP` share this schema:

| Column | Description |
|---|---|
| `submission_id` | Client-generated UUID used for retry/idempotency checks |
| `client_id` | Locally persisted device UUID |
| `guest_name` | Guest name |
| `attendance` | `YES` or `NO` |
| `message` | Optional message |
| `submitted_at` | Server-generated ISO timestamp |
| `source` | Constant such as `WEB` |

`guestSide` controls routing and does not need to be duplicated in the row because the destination tab identifies the side. The `SUMMARY` tab should show total responses, YES and NO counts for each side and overall. It must not calculate guest totals because guest count has been removed.

Google setup (later, with explicit authorization):

1. Create or select a Google Cloud project.
2. Enable Google Sheets API.
3. Create a service account.
4. Create the private spreadsheet under the host's Google account.
5. Share only that spreadsheet with the service account as Editor.
6. Store spreadsheet ID and credentials as Vercel environment variables.
7. Use separate spreadsheets/configuration for preview and production if practical.

## 8. Gift QR behavior

Display two clearly labeled cards:

- Bride: QR image, recipient/account label and bank label.
- Groom: QR image, recipient/account label and bank label.

Each card has an independent save/download action. QR images and labels are configuration/media, not hard-coded business logic. Both QR cards remain visible regardless of the side selected in RSVP. The site does not connect to a bank, validate transfers or write gift data to Sheets.

## 9. Security, privacy and reliability

- Google credentials exist only in server environment variables.
- Never commit `.env` files, private keys or actual credentials.
- Never call Google Sheets directly from browser code.
- Provide no public read endpoint for RSVP data.
- Do not log guest names or messages.
- Validate and normalize all input server-side.
- Sanitize spreadsheet cells to prevent formula injection.
- Add a honeypot and reasonable anti-abuse controls.
- Do not rely on function memory for rate limiting; serverless instances do not share durable state.
- Add shared-state or platform-level rate limiting only when justified and approved.
- Report success only after the Sheets write succeeds.
- Retry temporary Google errors with a small, bounded backoff; surface a safe retry message to guests.
- Back up/export the spreadsheet before the event.
- Test QR accuracy, RSVP writes and mobile behavior before distributing the invitation.
- Keep personal data to the minimum required for organizing the event.

## 10. Configuration model

The following must be replaceable without rewriting core components:

- Bride and groom names.
- Invitation text.
- Wedding date/time/timezone.
- Venue and map link.
- Photos and album ordering.
- Theme colors, fonts and decorative effects.
- Music file and initial muted/not-playing state.
- Bride/groom QR images and labels.
- Animation intensity and feature flags.

Secrets and environment-specific IDs belong in environment variables; public invitation content belongs in typed configuration files.

## 11. Delivery and platform workflow

### GitHub and Codex

- GitHub is the single source of truth.
- Per the project owner’s current instruction, Codex Cloud works directly on `main`; feature branches and pull requests are not required.
- `main` represents production-ready source.
- Important requirement changes must update this blueprint in the same pull request as related code.

### CI

GitHub Actions should eventually run:

- lint
- typecheck
- unit/integration tests
- production build

Use branch protection to require review and successful CI before merge when repository settings permit.

### Vercel

- Connect Vercel to the GitHub repository.
- Pull requests receive Preview Deployments.
- Merges to `main` may deploy production after the workflow is intentionally enabled.
- Do not deploy production without explicit user approval.
- Vercel MCP is optional for project/log inspection; it is not required to start implementation.

### Portability

- Static Vue/Vite output can move to another static host.
- Domain ownership remains independent of Vercel; migration is a DNS change.
- Keep Sheets access behind a repository interface.
- Keep use cases and validation independent from Vercel Functions.
- A new hosting adapter should not require rewriting invitation components or domain logic.

## 13. Definition of MVP readiness

The MVP is ready for production review when:

- All approved guest flows work on common iPhone and Android browsers.
- RSVP YES/NO records are written to the correct side tab.
- Duplicate retry behavior and safe failure states are tested.
- No guest-count field exists.
- Both gift QR cards are accurate and independently downloadable.
- Motion reduction, audio controls, image loading and accessibility checks pass.
- Credentials are absent from source and browser bundles.
- CI passes lint, typecheck, tests and build.
- Preview has been reviewed by the user.
- The user explicitly approves production deployment.
